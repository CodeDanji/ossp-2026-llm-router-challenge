PromptBudget v3 인수인계: delta-utility No-Go와 hash-regex 후속 실행

갱신일: 2026-08-27 · 대상: 다음 구현/평가 세션 · 기준 브랜치: codex/promptbudget-v3

현재 판정: delta-linear v3는 formal Train-only No-Go, hash-regex quality-objective 후속안은 승인된 별도 연구 track. 3 seeds × 5 grouped outer folds의 full nested-CV에서 delta-linear v3는 동일 outer-train으로 refit한 v2.1보다 가중 점수가 −0.042050 낮았고, 95% group-bootstrap CI는 [−0.050942, −0.033688]이었다. 이 결과는 v1 비교도, shipped all-Train v2.1 artifact 비교도 아닌 outer-refit v2.1과의 공정한 Train-only 비교다. 단, delta-linear의 No-Go를 hash-regex router의 성능 증거로 일반화하면 안 된다.

0. 현재 승인된 후속 track: hash-regex quality objective

고정: hash-regex feature family, fixed-family cost predictor, batch Lagrange allocator, Premium AX31 fill. 변경: quality prediction objective만 비교한다. 새 router family, 대규모 feature 재설계, exact knapsack은 범위 밖이다.

공식 규칙과 baseline/runtime을 다시 확인한 결과, content-only 및 ID/order permutation invariance를 지키는 batch-dependent allocation은 허용된다. 기존 hash_regex.select_models의 batch Lagrange 방식은 유지한다.

공식 decision record와 구현 명세는 다음 worktree에 있다. 구현에는 두 번째 문서만으로 충분하고, 첫 번째는 판단의 이유와 금지 범위를 학습할 때 참조한다.

  • decision record — 연구 근거, 반증, 결정 이유와 해석 경계
  • implementation plan — 구현, nested evaluation, finalization, Dev sanity의 실행 명세

작업 방식 제약: ponytail은 사용하지 않는다. 개선 가능성이 확인된 부분을 방치하지 않되, 사전 승인된 비교 이외의 복잡도는 추가하지 않는다.

1. 현재 결론과 실험 설계

  1. delta-linear v3를 재시도하거나 threshold를 완화하지 않는다. formal No-Go와 cost-slack 악화는 해당 family에 대한 확정 evidence다.
  2. hash-regex의 병목은 quality prediction이다. 공개 Dev counterfactual에서 full score 0.695369에 비해 quality oracle은 0.790653 (+0.095284), cost oracle은 0.705625 (+0.010256), 둘 다 oracle Lagrange는 0.803438이었다. exact DP는 oracle Lagrange 대비 +0.000341뿐이어서 exact knapsack은 제외한다.
  3. 실질 후보는 Raw, Weighted uplift, regret-weighted raw quality다. Direct uplift는 output equality를 확인하는 invariance control일 뿐 승자 후보가 아니다.
  4. 각 outer-train에서 cost head를 다시 fit하고, weight/λ/safety는 해당 outer-train의 inner grouped OOF에서만 정한다. 후보별 provisional safety는 complete allocator와 Premium fill을 포함해야 한다.
  5. 평가 우선순위는 prediction MSE가 아니라 최종 routing score, tier별 budget pass/cost ratio, fold 안정성이다. Dev는 승자 동결 뒤 한 번의 sanity check일 뿐 후보 선택·재튜닝에 쓰지 않는다.

1.1 사전 고정된 후보와 gate

2. 이전 delta-linear v3 기록 (보존용)

이후 section 2--10은 이미 종료된 delta-linear v3 연구의 원자료·실패 모드·재현 이력이다. 현재 실행 지시는 section 0--1과 11--12가 우선한다. 아래 기록을 근거로 hash-regex 후보를 배제하거나 delta threshold를 다시 조정하지 않는다.

이 작업은 SKT OSSP 2026 LLM Router Challenge의 PromptBudget 라우터 연구다. runtime은 prompt와 tier만으로 모델 ID 하나를 결정해야 하며, 실제 outcome·비용·ID·split·순서·네트워크를 사용할 수 없다. 공개 Train/Dev의 score/token/cost는 학습·검증에만 쓴다. tier 예산은 선택된 실제 비용으로 판정된다.

단계핵심 흐름과 관찰
v1all-Light 안전 baseline. 비용은 안전하지만 upgrade 품질 기회를 쓰지 못함.
v2모델별 absolute quality를 예측해 차감. 상대 이득과 비용 위험을 과대평가하는 문제가 관찰됨.
v2.1OOF monetary cost calibration과 공개 Dev policy calibration을 추가. 기본 shipped artifact는 absolute-linear v2.1이며 Dev weighted score는 0.670085227273.
v3 설계Light 기준 delta_quality, p_win, incremental_relative_cost를 별도 head로 학습하고, Train grouped nested-CV를 통과한 경우에만 Dev calibration으로 가는 research-only 후보를 정의.
이번 세션Train-only formal evaluator를 구현하고 full 3×5 grouped nested-CV를 실행. v3는 세 tier 모두 거의 all-Light로 붕괴해 outer-refit v2.1보다 낮은 점수와 높은 slack을 냄.

3. 합의된 의도와 의사결정

  • 사용자 요청: 서브에이전트는 보수적으로 활용하고, 테스트를 과도하게 늘리지 않는다.
  • v3는 배포 승격이 아닌 research-only delta-linear artifact다. v1/v2 loader 및 기본 resources의 호환성은 유지한다.
  • 공개 Dev 880은 “실제 결과를 보는 screening”에는 쓰되, formal Go/No-Go의 근거로 쓰지 않는다.
  • 초기 Dev 880 screening은 negative signal이었지만 formal evidence는 아니었다. 이후 사용자 명시 승인으로 full Train-only nested-CV를 실행했다.
  • formal comparator는 v3 vs outer-train-refit v2.1이다. v1이나 bundled all-Train v2.1 artifact와 비교한 결과로 해석하면 안 된다.

5. Windows 출력 문제: 원인과 수정

두 가지가 섞여 있었다.

  1. 실제 코드 결함, 수정 완료: README에 제시된 PYTHONPATH=src python -m promptbudget.runtime …는 module import만 하고 main()을 실행하지 않았다. src/promptbudget/runtime.py에 if __name__ == "__main__": raise SystemExit(main())를 추가했고, --help subprocess 회귀 테스트를 추가했다.
  2. 로컬 Windows 환경 특성: worktree의 build/promptbudget-v3 경로가 ReadOnly 속성을 상속해 output 생성에 부적합했다. screening output은 existing writable parent인 C:\tmp\promptbudget-v3-dev-screening에 썼다. runtime의 “output parent는 사전에 존재해야 한다” 계약은 바꾸지 않았다.

7. 원인 분석: 다음 설계가 해결할 문제

이 결과는 단순한 tier knob 문제로 취급하지 않는다. 먼저 아래의 signal·risk·policy 결합 문제를 새 설계의 가설과 측정 항목으로 분리한다.
  1. v3 policy collapse: 5,280 outer-test records에서 v3 route는 Fast Light 5,275, Balanced Light 5,270, Premium Light 5,249였다. Premium도 ax31 20회, Think 11회만 선택했다. 반면 outer-refit v2.1은 Balanced/Premium에서 각각 ax31 약 4,430/4,300회를 선택했다.
  2. ax31 quality signal의 분별력 부족: fold 평균 delta MAE 0.24, rank correlation 0.06, win AUROC 0.53이다. ax31 upgrade를 고를 근거를 거의 순위화하지 못한다.
  3. Think cost upper bound의 과도한 보수성: Think relative-cost MAE 112.56, p90 slack 625.76, p99 slack 1,670.57이다. win AUROC는 0.70이지만 upper-cost gate가 사실상 upgrade를 차단한다. 특히 long bucket의 Think p90/p99 slack은 1,698/3,128이다.
  4. Fast tier의 희귀 upgrade가 budget 불안정을 만듦: Fast는 단 5회 upgrade했지만 두 outer fold가 actual ratio 1.15 cap을 넘었다. 따라서 모든 upgrade의 평균 정밀도만으로 tier admission을 대표할 수 없다.
  5. 평가 구현의 향후 수정점: audit은 candidate tie-break가 spec의 p90 upper-cost slack 대신 max overspend를 사용하고, residual bucket fallback을 계산하지만 report에 남기지 않는 두 편차를 확인했다. 이번 negative conclusion을 무효화할 만한 크기는 아니지만, 미래에 positive/Go를 주장하려면 고치고 재실행해야 한다.
